## .gitignore Configuration

The repository uses a **whitelist strategy** where everything is ignored by default, and only specific files/directories are explicitly included.

## Documentation Files (docs/)

The `docs/` directory is **NOT tracked** in git. This is intentional to keep the repository focused on source code.

### Current Documentation Files

| File | Description | Date Created |
|------|-------------|--------------|
| `fixings_implementation_evaluation.md` | Comprehensive evaluation of fixings module | 2026-05-28 |
| `knockout_sheet_improvements.md` | Documentation of Excel Knockout sheet improvements | 2026-05-28 |
| `git_repository_structure.md` | This file - Git repository documentation | 2026-05-28 |

### Documentation Strategy

**Why docs/ is not tracked:**
1. **Rapid iteration** - Documentation can be updated frequently during development
2. **Local reference** - These docs are primarily for developer reference
3. **Deployment-specific** - May contain local paths and environment details
4. **Can be regenerated** - Documentation can be recreated from code analysis

**Alternative approaches:**
- Add `!/docs/` to `.gitignore` to track documentation
- Move critical docs to `README.md` files within tracked directories
- Use a separate documentation repository
- Add docs to a wiki or external documentation system

## Recommendations

### 1. Should Documentation be Tracked?

**Options:**

#### A. Track docs/ in Git (Recommended)
**Pros:**
- Version control for documentation
- Team members see latest docs
- History of documentation changes
- Documentation evolves with code

**Cons:**
- More git operations
- Potential merge conflicts

**Implementation:**
Add to `.gitignore`:
```gitignore
!/docs/
```

#### B. Keep docs/ Local (Current)
**Pros:**
- Cleaner commits
- Flexibility in documentation
- No merge conflicts

**Cons:**
- Documentation not shared
- Can become outdated
- Lost if working directory deleted

#### C. README.md Approach
Create `README.md` files in key directories:
- `ltv_app/README.md` - Application overview
- `ltv_app/blueprints/fixings/README.md` - Fixings module docs
- `tests/README.md` - Testing guide

**Pros:**
- Inline with code
- Discoverable
- Tracked in git

**Cons:**
- Scattered documentation
- Less detailed than separate docs

The `CLAUDE.md` file at the root should be tracked:

**Reason:** Critical for future Claude Code instances to understand the project.
